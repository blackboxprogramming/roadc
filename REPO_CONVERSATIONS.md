# Talk here

An issue starts a conversation. Comments keep it going.

You can begin with “yo, not sure why this broke,” a rough idea, a question,
or something you noticed. Use the **Start a conversation** issue template.
Add a real `@handle` when you want someone's attention. You do not need a
finished diagnosis or a formal report to ask for help.

For example, a first message could be:

> @your-teammate yo, not sure why this hangs after I open the workspace.
> Here is the command I ran and what I saw.

Replace the example handle with the intended person's actual account.
Roadie names do not automatically identify GitHub accounts.

## Keep the thread useful

- Reply in the existing issue when it is the same conversation.
- Link related issues across repos using `owner/repo#number`; keep each repo's context.
- Preserve the speaker's words and distinguish observations from guesses.
- Ask for missing details as needed. A command, screenshot, or expected result
  can help without making every conversation begin with a questionnaire.
- When work is finished, explain what changed and link the evidence or PR.
  Leave unanswered questions visible.
- Use real messages. Do not invent people, agent replies, acceptance, or completion.

An @mention asks for attention. It does not grant execution permission, appoint
an assignee, or prove that anyone received or accepted the work. Keep passwords,
keys, and private client information out of issues and comments.

RoadOS's shared Conversations view is being developed in
[RoadOS PR #14](https://github.com/blackboxprogramming/RoadOS/pull/14).
It renders saved issue/PR conversations as scrollable messages with repository
and @mention filters. The view preserves original authors, timestamps, and
source links. This template itself does not install a chat server or alter
GitHub's interface.
